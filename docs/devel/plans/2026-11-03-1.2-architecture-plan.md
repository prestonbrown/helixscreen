## 3. Batch 1: layering and include fan-in (#1946, #1954, #1953, #1952)

From `review-includes-layering.md`, spot-checked: `i_moonraker_client.h:13` includes
`printer_discovery.h` for a by-value `hardware()` return at `:182`; `printer_discovery.h:16`
includes `ams_types.h`; `advanced_panel_types.h:22` includes `spoolman_types.h` for a comment;
`spoolman_types.h:384` and `chamber_heater_backend.h:125` hold the inline bodies that need
complete types; `Makefile:845` force-includes `lvgl_pch.h`; Android already precompiles that
header (`android/app/jni/CMakeLists.txt:356`); CI's ccache sets no pch sloppiness; 45 of 87
`src/api` files are not Moonraker.

Findings that change the issues:

- **The forced include is the per-TU floor.** Five single-file syntax checks cost 3.6-4.5 s
  each whether the TU is 11 lines or `printer_state.cpp`: `lvgl_pch.h` (LVGL ~107K lines,
  spdlog 19.5K, json 25.5K, helix-xml) dominates every parse. So the header cuts in #1954 buy
  **rebuild fan-out** (an AMS header edit stops rebuilding half the tree), not parse time;
  only #1953 moves parse time.
- **#1954 is four bridges, not one.** `ams_types.h` reaches 522 of 1,166 src TUs (1,644 of
  2,996 with tests). Cutting `printer_discovery.h -> ams_types.h` alone gives 522 -> 492,
  because `spoolman_types.h` (inline `apply_spool_to_slot` needs `SlotInfo` complete),
  `filament_display_name.h` (`const SlotInfo&` only) and `chamber_heater_backend.h` (inline
  `DryerInfo` default) each carry it to the same ~285 TUs. All four cuts: **522 -> 259**. After
  that the by-domain split of the 2,837 lines is optional.
- **#1953 is bigger than its text.** 790 TUs reach `hv/json.hpp` through their own includes
  (144 headers include it directly, 94 of them could take a forward declaration); only 376 see
  it solely through the forced include. A real `json_fwd.h` alone drops reach 789 -> 762. The
  forward declaration must copy libhv's bundled `basic_json` template parameter list exactly.
  Dropping json from `lvgl_pch.h` needs ~60 TU + 2 header include edits; spdlog, 5.
- **A real PCH is feasible but not yet**: Android proves the header is PCH-clean on clang, but
  CI's ccache has no `pch_defines,time_macros` sloppiness, ten cross toolchains plus ASAN/TSAN
  plus per-command gate defines mean one PCH per flag set, and gcc silently ignores a
  mismatched `.gch` (a stale PCH is a slow build with no error). Only after the json/spdlog
  drop, measured with `-ftime-trace`, with a proof step that the PCH is used.
- **The big upward edges are plumbing misfiled, not UI.** ui -> application 152 edges
  (`static_panel_registry.h` 67, `static_subject_registry.h` 34, `data_root_resolver.h` 12),
  api -> system 85 (`text_io.h` 26, `runtime_config.h`, `config.h`, `log_redact.h`,
  `http_executor.h`), printer -> ui 64 (`display_numbering.h` 14, `observer_factory.h` 13,
  `ui_toast_manager.h` 9). `src/printer` has 68 `ui_*` include lines in 34 files today (the
  audit's 103 has shrunk). The real UI reached from below (#1952) is `ToastManager::instance()`
  at 13 sites, `ui_insert_notice.h` in 8 backends, `ui_notification.h`, and modal/nav/overlay
  headers in 4 files; none of those includes is dead.
- **The mock client lives in the network layer and populates printer state** (api -> printer
  46 edges, 16 files, all `moonraker_client_mock*`): a test double in the wrong directory.
- `i_moonraker_api.h` returns its ten sub-APIs by reference, so ten forward declarations
  replace a 722-line include for 126 of its 193 includers.

Proposed layers (low to high): L0 core (util, config, generated, plus the moved plumbing),
L1 platform (network, bluetooth, input, display/wifi/usb/ethernet from api), L2 moonraker (the
Moonraker half of api), L3 state (printer, temperature, spoolman, print, calibration, sensors,
led, plugin, system services), L4 rendering, L5 ui, L6 app (application, abort, remote, tools).

Findings that change the issues:

- **#1958 after #1983 is about intent, not crashes.** `ModalStack` entries are `WeakWidget`s, so
  `Modal::hide(stale)` warns and returns instead of touching freed memory. The 23 bare sites
  (7 `Modal::show("...")` + 16 `modal_show(`) split into: 11 raw members cleared by hand
  (behavior risk: a stuck re-entry guard, address reuse), 3 with a DELETE self-clear, 6 already
  `WidgetRef`, 3 discarded. 27 raw `*modal*`/`*dialog*` members remain in 23 headers; `ModalGuard`
  has zero users and the docs still recommend it. The one crash-shaped leftover is
  `Modal::dialog_` itself.
- **#1959's "~170 never released in 34 files" does not reproduce.** 361 raw init sites in 77
  files, but 46 of those files register the subject with a `SubjectManager` right after. The
  genuinely unmanaged set is **44 sites in 7 files** (`buffer_status_modal` 17,
  `ui_ams_context_menu` 15, `detection_manager` 5, cfs/indx device flows 2+2, two singles).
  The larger number is static storage: 322 file-scope + 35 in-class static subjects, of which
  ~150 sit in per-instance `PanelWidget` subclasses. Those cannot move to members for 1.2:
  the XML engine has one global name scope, so per-instance subjects need per-instance names
  it does not have. The right target there is static storage + one file-static manager +
  `StaticSubjectRegistry` deinit, which `tool_switcher_widget.cpp` already does; 13 widget
  files lack the registry line.
- **#1246's prerequisite is met** (`deinit_all` withdraws names and debug entries), and its
  `destroy_on_close=true` parameter no longer exists: the policy is the virtual, 24 overlays
  return true, 3 free through their own close path, so **27 of 80 overlays free the tree,
  1 frees subjects, 0 of 12 panels free anything**. Flipping the base default would break 19
  overlays that cache raw widget pointers with no `on_ui_destroyed()` (history dashboard 16,
  history list 7, fan control 5, retraction 5, timelapse settings 5, ...) and 3 with timers that
  outlive the tree; 25 overlays have zero raw members and flip for free.
- **#1878 layout variants**: of eight variant files, one is a delete
  (`portrait/print_status_panel.xml`, identical in effect), five fold into `bind_style_if_eq`
  on `ui_breakpoint` or a `row_wrap` (`material_temps_overlay` x2, `theme_preview_overlay`,

  stays for those two. The header fold is the highest-payoff one: it feeds 22 screens, has
  already drifted (lost the `style_max_height` cap), and needs one decision: micro headers at
